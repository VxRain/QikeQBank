# 图片资源同步 v2：把「图片」从同步数据改成内容寻址缓存

> 前置数据：`docs/asset_sync_bench.md`（100 万题 / 10 万图实测）
> 被替代的设计：`question_assets` 派生索引增量维护版（已据实测否决，结论见本文 §0 与 `docs/asset_sync_bench.md`）
> 状态：方案稿，未落地

---

## 0. 先回答"到底谁错了"

不是"设计稿和我的改版都没解决问题"，而是**三者都把坐标定错了**。分开说：

| 判断 | 是否成立 | 依据 |
|---|---|---|
| 设计稿的核心前提："两处 O(全库题目) 的图片操作"是性能问题 | ❌ **不成立** | 100 万题全库扫描 8.0 s，seed 总计 10.6 s，且每设备**只跑一次** |
| 设计稿的技术细节：派生缓存、不给 `assets` 建外键、不进同步协议、不用触发器 | ✅ 成立（但这些细节服务的是一个不存在的瓶颈） | — |
| 设计稿要把 GC 切到派生表 | ❌ **反向有害** | GC 全扫 8 s；表缺行会导致**不可恢复的删图** |
| 我的方案 B（按需物化，同样是给扫描/GC 建索引） | ❌ **同一坐标下的另一个变体，同样错** | 同上：只省一次性 7.7 s |
| 我说"写路径钩子代价很大" | ❌ **被数据推翻** | 事务内 refresh 17.8–25.6 µs/题，裸写题 26 µs/题，同量级 |
| 我提的 GC"候选 LIKE 兜底" | ❌ **被数据推翻** | 6.6 s/候选 ≫ 一次全扫 8 s |
| 我指出的真瓶颈：串行网络 + 逐图提交 + 待办 JSON + 逐题回读 | ✅ 成立且已量化 | 100 min 网络 / 95 s 提交 / 46 ms×包 / 57 s per 1M base |

**一句话**：`question_assets` 是一张**功能表**（反向查询），被当成**性能方案**来设计了。
性能问题在传输层，不在查询层。

## 1. 重新定位：图片是缓存，不是同步数据

现在代码里图片被当成"必须同步到位的业务数据"（`s3_asset_download_pending` 是"待办"，
必须搬完）。但它具备三个性质，说明它其实是一次 **HTTP 缓存填充**：

1. **内容寻址**：key = sha，对象不可变（`assets.rs:30`，`s3/mod.rs:42`）；
2. **幂等**：重复取同一个 sha 结果完全相同（`assets_put_bytes_impl` 已做去重）；
3. **可丢弃**：本地丢了只需重新取（本地是副本，桶才是源）。

由此推出三条设计原则，后面的每一层都从这三条派生：

- **P1**：本地缺图不是"同步未完成"，是"缓存未命中"——按需取，允许长期不取。
- **P2**：缓存填充必须能被打断、续传、放弃、限速；不能阻塞 UI 或持锁。
- **P3**：判断"要取哪些图"应该在**数据到达时**就知道（manifest），不该回头扫全库。

## 2. v2 架构：五层

### A 层：传输 → 并发 worker + 文件先行 + 批量入库

**现状**（`s3/sync.rs:1234` `pull_assets`）：单线程、阻塞 `ureq`、逐 sha
`GET → sha256 → 写文件 → INSERT`，每条 INSERT 各自 autocommit，全程持有
`Mutex<Connection>`。

**实测**：冷下载 **1576 µs/图**（其中落盘 ~619 µs、逐图提交 ~950 µs）；10 万图串行
网络 ≈100 分钟。

**改法**：

```
                ┌──────────── main thread（持锁，短）─────────────┐
  asset_jobs ──▶│ 取一批 sha(≤500) → 派发 → 释放锁 → 接收结果         │
                │ 结果按 500 条一批：INSERT OR IGNORE INTO assets    │
                └───────────▲───────────────────────┬─────────────┘
                            │ channel                │
        ┌───────────────────┴────────────────────────▼─────────────┐
        │ worker × N（4–8，按 CPU/设置）——只碰文件系统，不碰 DB      │
        │ GET → 校验 sha256 → 写 assets/<2hex>/<rest>.<ext>（幂等）  │
        └───────────────────────────────────────────────────────────┘
```

- worker 写的是**最终路径**（内容寻址），中途崩溃 = 文件已存在 = 幂等跳过。
- DB 记账与文件写分离：只要文件在，`asset_file_present` 就为真（它查的是登记行
  + 文件）。为了不出现"文件在、登记行缺 → 反复重下"，启动时对 `assets/` 目录做一次
  **单向对账**（目录有、登记无 → 补登记行；这是幂等的、O(本地文件数)）。
- 并发度可配，默认 `min(8, max(2, cpu/2))`。

**收益**：本地 1576 → ~650 µs/图（10 万图 158 s → 65 s 单线程口径，且可再并行）；
网络 100 min → 12.5 min（8 并发）。

### B 层：队列 → `asset_jobs` 表替代 `db_meta` 里的 JSON

**现状**：`DOWNLOAD_PENDING_KEY` / `PENDING_ASSETS_KEY`（`s3/sync.rs:47,54`）是两个
`db_meta` 里的 JSON 数组。每次合并都 load→parse→serialize→写回**整串**。

**实测**：待办 10 万条时 **46 ms/次**，文本 6.3 MB；200 个日志包 ≈ **1.23 GB 重复写**。
更糟：`not-in-bucket` 的项会**永久留在待办**，每轮 pull 重新 GET 一遍 404。

**改法**：

```sql
CREATE TABLE IF NOT EXISTS asset_jobs (
  sha         TEXT PRIMARY KEY,
  kind        TEXT NOT NULL,              -- download | upload
  state       TEXT NOT NULL,               -- pending | dead
  attempts    INTEGER NOT NULL DEFAULT 0,
  last_error  TEXT,
  next_try_at TEXT,                        -- 指数退避（毫秒级时间戳字符串，可比较）
  priority    INTEGER NOT NULL DEFAULT 0,  -- 0=预热 1=按需（当前渲染）
  updated_at  TEXT NOT NULL
);
CREATE INDEX IF NOT EXISTS idx_asset_jobs_due ON asset_jobs(kind, state, next_try_at);
```

- 完成即**删行**（不保留 done，表始终只含"待做/死信"）。
- `not-in-bucket` → `state='dead'`，不再重试；UI 提供"重试死信"。
- 批量入队：`INSERT OR IGNORE` 一条语句进 500 条。

**收益**：46 ms → <0.5 ms/包；1.23 GB → ~0；404 风暴消失。

### C 层：manifest → 让"要取哪些图"随数据到达

**现状**：接收方靠 `applied_log_asset_refs`（`s3/sync.rs:542`）**逐题 `fetch_question`
回读本地库**再解析 JSON 求 refs。

**实测**：56.6 µs/题 → 1000 题包 57 ms（可接受）；但 100 万题 base ≈ **57 s** 白花。

**改法**：上传方**已经算好了** refs（`upload_assets`，`s3/sync.rs:626`），写进信封头：

```json
{"k":"h","format":1,"device":"…","seq":42,"rows":880,
 "assets":["<sha>","<sha>", "…"]}
```

- `wire::decode`（`wire.rs:117`）只读已知字段，未知字段原样保留 → **老/新版本互相兼容**。
- 接收方：有 `assets` 就直接批量入 `asset_jobs`；没有（老对象）→ 回退到
  `applied_log_asset_refs`。回退路径保留一个版本周期后删除。
- `compact`（`s3/sync.rs:1272`）生成的 base 同样带 manifest → **新设备不扫题目就知道要什么**。

**收益**：57 s/1M → 0；**并且 `seed_download_pending` 的全库扫描几乎不再需要**
（仅升级老库时保留一次，8 s，一次性）。→ 设计稿要解决的那个问题，在这一层被顺手消灭。

**已知 trade-off**：manifest 由发送方按它导出的行算，可能包含本地 LWW 已拒收的旧图
→ 最坏是多取一张桶里不存在的图 → 404 → `dead`。图片是幂等缓存，这个损失可接受。

### D 层：触发 → 首屏按需 + 窗口预热（"不卡"的关键）

**现状**：新设备首次 pull 会尝试把**全库**图搬完，界面上就是"转圈两小时"。

**改法**：

| 时机 | 动作 |
|---|---|
| `assets_resolve` 未命中（`assets.rs:150`） | 入队 `priority=1`，**同步等一次单图 GET**（超时 2 s）→ 当前渲染的图立刻出来；失败显占位符 |
| 进入题库 / 开始练习 | 该库最近 200 题引用的 sha 入队 `priority=0`（窗口预热） |
| 用户点「下载全部图片」 | 全量入队，显示进度、可暂停（同一队列，只是 priority/批量不同） |
| 默认 pull | **不再**自动全量下载，只入队 |

**收益**：首屏从"等全量"变成"秒级"；后台搬运对用户不可见。

### E 层：base 分片（规模必需，与图片无关但同属首次同步体验）

**现状**：`compact` 导出**单个** gz 对象（`s3/sync.rs:1272`）。1M 题命名空间 ~2.1 GB
（实测库 2143 MB），gzip 后仍是数百 MB 单对象：无断点、无分片校验、单请求失败重来。

**改法**：`base/<ts>-<device>/part-000.ndjson.gz …` + `manifest.json`（分片清单、
每片 sha、rows、该片 `assets` 集合）。拉取按片：下载 → 校验 → 单事务 apply → 落游标。

## 3. 目标指标（用现有基准脚本验收）

| 场景 | 现在（实测/推算） | v2 目标 | 由哪层解决 |
|---|---|---|---|
| 新设备首屏可刷题 | 等全量 ≈ 100 min+ | **< 3 s** | D + C |
| 10 万图搬完（显式动作） | 100 min，UI 冻结，无进度 | **< 15 min**，可暂停续传 | A + B |
| 图片本地开销 | 1576 µs/图 | **< 700 µs/图** | A |
| 每包待办更新 | 46 ms + 1.23 GB/200 包 | **< 0.5 ms**，0 放大 | B |
| 1M base 的 refs 提取 | 57 s | **~0** | C |
| 100 万题首次 seed 扫描 | 10.6 s | **0（新库）/ 8 s 一次性（升级）** | C |
| GC | 8 s 扫描 + 删文件 | 不变（**继续全扫，不要索引**） | — |
| base 单对象体积 | 数百 MB 无断点 | **< 200 MB/片，可续传** | E |

验收方式：`bench_assets.rs` 已能测第 2/3/4/5/6 行；A、B 层落地后各加一个 case
（"批量提交后的 µs/图"、"队列合并 ms/包"），E 层加"分片 base 端到端 apply"。

## 5. `question_assets` 的最终裁决

**不做增量维护版。** 理由（全部来自实测）：

- 唯一净收益是"首次 seed 少扫 8 s"，而 C 层落地后这个消费者本身消失；
- GC 用它有**不可恢复删图**风险，而 GC 全扫只要 8 s；
- 写钩子在事务内确实便宜（17.8–25.6 µs/题），但便宜不等于值得——没有消费者。

**保留一种形态**：反向查询（"这张图被哪些题用了"）作为**可选功能**，
`question_assets` 只在需要时物化一次：

```
question_assets_rebuild()   // 全库扫一遍写表：28 s / 100 万题（实测）
question_assets_dropped()   // 退出应用时删表（或干脆用临时表 / ATTACH 内存库）
```

不挂写路径、不进同步协议、不做 verify/backfill、GC 不用它。
只有当「图片管理 UI」变成常态功能（引用计数、批量查看未引用图）时，才升级为增量维护。

## 6. 兼容与迁移

| 事项 | 处理 |
|---|---|
| `SCHEMA_VERSION` | 新增 `asset_jobs` 是 additive，`init_schema` 每次启动跑 `CREATE IF NOT EXISTS` → **保持 3**，不需要迁移（`seed_db_meta` 是 `INSERT OR IGNORE`，永不更新版本，现有版本号也无读者） |
| 老 `db_meta` 待办键 | 首次启动读出 → 批量搬进 `asset_jobs` → 删除旧键（一次性） |
| 老对象无 manifest | 回退 `applied_log_asset_refs`，保留一个版本周期 |
| 老客户端读新对象 | header 多一个字段，`decode` 忽略未知字段 → 安全 |
| 文件在、登记缺 | 启动做一次目录→登记的单向对账（幂等） |
| 桶里没有的图 | `dead` 终态 + UI 死信列表，不再每轮重试 |

## 7. 还需要补的两个测量（本次没覆盖）

1. **1M 题 base 的端到端**：`export_delta_at(None)` → `wire::encode` → gzip → 空库
   `decode` → `apply_bundle`。这决定"新设备元数据建库"的真实耗时与对象体积（占首屏
   第二大头）。基准脚本已有 1M 库的造数，直接复用即可，估计半小时内可出数。
2. **真实 S3 的 RTT/吞吐**：本次用 60 ms 假设。用真实端点拉 100 张图测一次，
   替换 `网络折算` 的口径（决定 P1 的并发度与是否需要限速）。

在拿到这两个数之前，P0 三项不依赖它们（收益是本地开销和写放大，与网络假设无关），
可以立即开工。

## 8. 需要拍板的点

1. 是否接受"**图片不默认全量下载**"（首屏按需 + 窗口预热）？这是"不卡"的根本前提，
   也是唯一会改变用户可感知行为的决定。
2. `asset_jobs` 用表（推荐）还是沿用 `db_meta` JSON + 只做批量提交？
3. 并发度：固定 8，还是暴露为设置项 + 自动按 CPU/带宽调整？
4. `not-in-bucket` 进 dead 是否需要"自动重试一次"（应对对端还没上传完的时序窗口）？
5. base 分片按题库切还是按行数切（前者对"只同步某个库"友好，后者分布均匀）？
6. P4 反向查询：现在做（1 d），还是等图片管理 UI 需求出现再做？
